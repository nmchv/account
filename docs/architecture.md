# Архитектурные заметки

## Слои

- `index.html`, `styles/` — адаптивная оболочка и разделы кабинета.
- `scripts/app.js` — навигация, отображение состояний и пользовательские действия.
- `scripts/config.js` — публичная конфигурация Supabase; секретные ключи здесь недопустимы.
- Supabase Auth — регистрация, вход и управление сессией. Клиент использует только сессию текущего пользователя.
- PostgREST — чтение профиля, публичного реестра проектов, назначенных доступов и пользовательских данных. Каждая таблица должна быть защищена RLS; UI-фильтры не являются контролем доступа.
- `supabase/migrations/20261115000000_account_core.sql` — схема кабинета, публичный каталог сервисов и защищённые пользовательские данные. Для общего проекта сначала примените миграцию Exam Trainer `20261107000000_initial.sql`, затем эту миграцию.
- `sw.js` кэширует только статические файлы оболочки и не кэширует API или пользовательские данные.

## Ожидаемые данные

Общий идентификатор профиля — `profiles.id`, равный `auth.users.id`, как в Exam Trainer. Миграция кабинета добавляет к профилю поля `avatar_url`, `bio`, `preferred_language` и `timezone`; не создавайте параллельный профиль с отдельным `user_id`.

Кабинет использует `projects`, `user_project_access`, `user_activity`, `achievements`, `user_achievements`, `user_goals` и `notifications`. Попытки Exam Trainer попадают в журнал активности триггером после завершения. GeoTrainer сохраняет попытки в `geotrainer_attempts` и предлагает выбрать старый локальный профиль для импорта; этот перенос нужно подтвердить на каждом устройстве. `service_data` служит расширяемым хранилищем для новых сервисов, но чувствительные или проверяемые результаты должны иметь отдельные таблицы и серверную валидацию.

## Границы доверия

- Пользовательский идентификатор берётся из подтверждённой сессии Auth, а не из формы или URL.
- RLS должна ограничивать профили, события, цели, уведомления, доступы и достижения владельцем строки. Публичный реестр проектов должен раскрывать только разрешённые к публикации записи.
- Проверка проекта, приём событий, выставление результата и начисление XP требуют серверной проверки. Клиент кабинета не отправляет события от имени других проектов.
- Администраторы определяются таблицей `public.admins` и функцией `public.is_admin()` (миграции `20261115120000_account_admin.sql` и `20261115130000_account_admin_full.sql`). Админ входит обычным паролем Supabase Auth; кнопка «Админка» в интерфейсе ничего не разрешает — чтение чужих данных и запись доступов, достижений, уведомлений и статусов сервисов ограничены политиками RLS. Назначать админов можно только из SQL Editor или `service_role`. «Просмотр кабинета» пользователя — это чтение его данных, а не вход под его учётной записью.
- Один проект Supabase даёт общий аккаунт Auth, но не переносит сессию между разными доменами. Настоящий SSO потребует отдельного OIDC-провайдера; до его настройки пользователь входит на каждом домене теми же почтой и паролем.
- В браузерной конфигурации допустим только публичный publishable/anon key. `service_role` и секреты остаются только в Edge Functions/серверном окружении.
